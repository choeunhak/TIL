## Chapter 13. Automation and Tooling

### 1. 자동화의 목적과 수준

자동화의 목적은 단순히 사람을 없애는 것이 아니다. 반복 작업과 긴급 대응에 드는 시간을 줄이고, 작업 결과의 일관성을 높이며, 서비스와 조직이 커져도 운영이 비례해서 늘어나지 않게 하는 것이다. 자동화 자체가 신뢰성 목표를 대신하지는 않으며, 나쁜 절차를 빠르게 반복하면 위험도 같이 증폭된다.

- **수동**: 사람이 판단하고 명령을 수행한다. 새롭거나 모호한 작업의 실제 절차를 이해하는 데 유용하지만 빈도가 늘면 병목·오류가 된다.
- **부분 자동화**: 컴퓨터가 탐지·계산·준비를 맡고 사람은 승인이나 판단을 한다. 안전성과 속도의 절충점이 될 수 있다.
- **완전 자동화**: 감지부터 실행·검증까지 시스템이 수행한다. 빠르고 일관되지만, 잘못된 입력이나 잘못된 정책이 넓은 범위에 즉시 영향을 줄 수 있다.

자동화는 한 스크립트에 국한되지 않는다. 개별 서비스의 로컬 도구, 여러 서비스가 공유하는 플랫폼, 시스템에 내재된 자동 복구 동작까지 스펙트럼이 넓다. 적합한 수준은 작업의 반복성·모호성·피해 규모·복구 가능성에 따라 결정한다.

### 2. 규모가 커질 때의 자동화

자동화는 증가하는 운영량을 흡수해 팀의 선형 성장 없이 서비스를 확장하게 해준다. 하지만 서비스의 구성·지역·테넌트·버전이 늘면 자동화 입력과 상태의 조합도 급증한다. 플랫폼의 추상화는 사용자가 필요한 튜닝을 할 수 있도록 하면서도 불필요한 조합과 특수 사례를 제한해야 한다.

#### 용량 프로비저닝 사례

용량 관리는 수요 신호를 읽고, 목표 용량을 계산하며, 자원을 확보·배치하고, 실제 효과를 확인하는 반복 과정이다.

- 단기(분~시간): 복제본 수·자원 할당을 조절해 급격한 변동에 대응한다.
- 장기(일~월): 수요 예측과 공급 계획을 맞춰 데이터센터·하드웨어 등의 제약을 다룬다.
- 성숙 단계: 초기 프로토타입에서 시작해 관측·승인·실행·검증을 단계적으로 자동화한다. 초기부터 모든 서비스를 무인으로 관리하려 하면 예외와 미성숙한 신호가 위험을 만든다.

#### 인시던트 관리 사례

공통 인시던트 대응 시스템은 영향 범위 파악, 담당 역할 지정, 상황 공유, 타임라인 기록, 사후 학습 같은 반복 절차를 자동화할 수 있다. 공통 도구는 서비스별 대응 편차를 줄이지만, 사건별 판단과 책임 소재를 없애지는 않는다. 자동화된 조정은 명확한 상태와 소유자를 노출해야 한다.

### 3. 자동화의 역설과 함정

자동화는 수작업을 줄이는 동시에 감시·유지보수·예외처리라는 새 일을 만든다. 특히 시스템이 대부분 정상일 때 인간의 숙련이 약해지고, 자동화가 실패하는 순간에는 사람이 낯선 상황을 더 빨리 처리해야 한다.

- **위험한 자동화**: 잘못된 신호가 대량의 변경으로 이어질 수 있다. 속도 제한, 범위 제한, 단계적 실행, 회로 차단기, 롤백 경로를 둔다.
- **기술·판단력 저하**: 사람이 절차를 잊지 않도록 연습·시뮬레이션·명확한 수동 경로를 유지한다.
- **자동화 놀람**: 시스템이 왜 행동했는지 알 수 없으면 운영자는 제어감을 잃는다. 입력·판단·실행·결과를 설명하고 이벤트와 로그를 남긴다.
- **기초 설계 결함 은폐**: 반복 복구 자동화가 잘못된 아키텍처나 잦은 장애를 정상처럼 보이게 할 수 있다. 증상 완화와 근본 문제 해결을 분리한다.
- **움직이는 표적**: 자동화가 의존하는 API·환경·정책이 바뀌면 조용히 실패할 수 있다. 호환성 계약, 테스트, 소유자를 둔다.
- **모호한 입력**: 잘못된 상태를 “추측해서” 처리하는 대신 안전한 기본값과 명시적인 중단 조건을 사용한다.

### 4. 자동화 여부를 결정하는 비용 분석

정량 비교의 출발점은 자동화의 초기 구축비와 수명 동안 유지비를, 수동 작업의 회당 시간과 발생 빈도에 비교하는 것이다.

`자동화 비용 ≈ 초기 구축 비용 + 유지 비용 × 수명`

`수동 비용 ≈ 회당 작업 시간 × 발생 빈도 × 수명`

숫자만으로 결정할 수는 없다. 안전성, 전략적 중요도, 작업의 모호성, 사용자의 불편, 자동화 실패 시 피해, 팀의 인지 부담도 평가한다. 특히 낮은 확률의 대형 피해나 유지보수의 숨은 비용을 무시하지 않는다.

### 5. 사례가 주는 설계 원칙

- 하드웨어 결함 격리 자동화는 트래픽을 우회해 장애를 완화할 수 있지만, 한 지역에서 너무 많은 용량을 동시에 제거하지 않도록 상한과 검증을 둔다.
- 지역 출시 도구는 팀마다 rollout·모니터링을 새로 만드는 대신 공통 플랫폼을 제공해 비용을 낮춘다.
- 메모리 누수 프로세스를 자동 재시작하는 것은 일시적 완화책이다. 재시작이 빈번해지면 근본 결함을 숨기는 안티패턴이 된다.
- Traffic Director 사례에서는 다중 단일 테넌트 구조가 초기에 격리와 제품 속도를 제공했지만, 서비스·지역·테넌트 조합이 커지자 단일 설정의 조합 폭발과 rollout 정체가 나타났다. 플랫폼의 확장 한계와 제품 아키텍처를 함께 재검토하고, 작은 rollout·설정 단순화·필요한 자동화의 일시 중단을 거쳐 구조를 다시 설계했다. 처음의 설계가 틀렸다는 뜻이 아니라, 운영비가 커질 때 아키텍처를 다시 선택해야 한다는 뜻이다.

### 6. 점진적 자동화

“직접 해 보고, 반복을 이해하고, 그다음 자동화한다”는 순서가 안전하다. 관찰만 하는 모드에서 추천 모드, 승인 후 실행, 실행 후 알림, 완전 자동 실행 순으로 신뢰 수준을 올릴 수 있다. 성공 조건·실패 처리·감사 로그까지 포함해야 자동화가 실제로 작업을 끝낸다. 일부 명령만 자동화하고 마지막 복구·검증을 사람에게 남겨두면 오히려 부담이 커질 수 있다.

### 7. Toil 이해와 측정

Toil은 수동적·반복적이며 시스템 성장에 따라 함께 늘고, 지속적인 가치가 제한적인 운영 작업이다. 알려진 flaky test 재실행, 자주 죽는 프로세스의 수동 재시작, 백업 검증의 반복 등이 예다. 어렵거나 싫은 일이라고 모두 toil은 아니다. 장애 원인 수정, 보안 정책 개선, 재발 방지 테스트는 장기 가치를 만드는 엔지니어링이다.

Toil은 엔지니어링 시간을 잠식해 제품 개선을 늦추고, 팀의 피로·이직·장애 위험을 키우는 악순환을 만든다. 대책을 세우기 전 기준선을 측정한다.

- 특정 작업별 소비 시간과 반복 빈도를 기록한다.
- 당직 호출 중 실제 행동이 필요한 비율과 잡음을 구분한다.
- 운영 작업과 기능·신뢰성 개선에 쓰는 시간을 함께 본다.
- 지표는 자동화 성공 여부뿐 아니라 toil 감소, 실패·재작업, 사용자 영향까지 연결한다.

#### Toil에 대응하는 방법

1. 유발 요인(불안정한 테스트, 불완전한 제품 기능, 권한 설계)을 먼저 찾는다.
2. 제거·제품 수정·설계 변경·도구 개선 중 지속 가능한 해법을 택한다.
3. 당장 자동화가 어렵다면 필요한 작업인지, 중단할 수 있는지 검증한다.
4. 일시적 수동 작업이라면 소유자와 종료 시점을 정한다.
5. 사람의 판단이 필요한 복구는 자동화가 단계를 수행하더라도 핵심 승인 지점에 사람을 둔다.

데이터베이스 복구 사례에서 팀은 사고 중 실행한 명령을 그대로 하나로 묶는 대신, 읽기/쓰기 차단, 복구, 다운스트림 조정, 재개처럼 재사용 가능한 논리 연산으로 나눴다. 복구 시작 여부는 사람이 결정하도록 남겼다. 모니터링 오작동이 모든 경보를 울린 직후였기 때문에, 완전 자동 복구였다면 불필요한 restore로 최근 데이터를 잃을 수 있었다.

#### 하지 말아야 할 toil

- 제품에 빠진 기능을 SRE의 영구 수작업으로 메우지 않는다. 결함은 제품 소유팀이 고쳐야 한다.
- 머신·사용자·기능 수에 따라 빠르게 늘어나는 toil은 방치하지 않는다. 제거, 중단, 더 적합한 소유팀 이관을 검토한다.
- 과도한 권한 도구를 SRE만 쓸 수 있다는 이유로 사람의 반복 작업을 정당화하지 않는다. 책임이 하나인 좁은 도구와 최소 권한이 더 안전하고 자동화하기 쉽다.

### 8. 인간 중심 자동화

부분 자동화는 사람과 시스템의 팀워크다. UI의 기본값·명칭·오류 설명은 신뢰성 요소다. 작업 상태가 보이도록 지표·로그·대시보드를 제공하고, 자동화가 실패했을 때 사람이 원인을 파악할 수 있어야 한다. 자동화가 사람의 승인 큐에 너무 많은 일을 보내지는 않는지, 속도 증가로 경합·순서 가정이 드러나지는 않는지 검토한다. 새 도구가 팀의 기술 수준·이직률·교육 부담에 맞는지도 고려한다.

**적용 체크리스트**

- 자동화할 문제와 원하는 사용자 결과가 정의되어 있는가?
- 비용·빈도·위험·모호성·유지보수 책임을 평가했는가?
- 범위·속도 제한, dry-run/단계 실행, 중단·롤백이 있는가?
- 판단 근거와 현재 상태를 운영자가 확인할 수 있는가?
- 도입 후 toil 및 사용자 영향을 다시 측정할 계획이 있는가?

## Chapter 14. Testing

### 1. 테스트의 목표와 기본 모델

테스트는 코드가 의도대로 동작하는지 확인하는 데 그치지 않고, 실제 배포 환경에서 변경이 사용자에게 미칠 위험을 줄이는 신뢰성 수단이다. 작은 범위의 빠른 검증과 실제 환경에 가까운 검증을 층으로 배치한다. 한 종류의 테스트로 모든 실패를 잡을 수 없으므로, 결함 발견 시점·비용·현실성 사이에 균형을 둔다.

- 개발자 수준의 단위 테스트는 좁고 빠르며 논리를 검증한다.
- 통합·시스템 테스트는 경계와 구성 요소 간 상호작용을 확인한다.
- production에 가까운 테스트는 실제 부하·의존성·운영 설정 차이를 드러낸다.
- 테스트 결과는 “통과”뿐 아니라 어떤 위험을 검증했는지 설명해야 한다.

테스트 모델을 설계할 때에는 테스트 대상의 중요도, 결함의 영향 반경, 환경 간 차이, 피드백 속도, 유지비를 살핀다. 테스트가 너무 느리거나 flaky하면 팀이 우회하거나 무시하게 되므로 안정성과 신뢰가 필수다.

### 2. 테스트 유형과 시작 방법

기본은 대표적인 사용자 동작과 중요한 실패 경로를 식별하고, 각 경로에 가장 빠르고 현실적인 검증을 연결하는 것이다. 새 시스템에 처음부터 거대한 테스트 체계를 요구하기보다 핵심 경로부터 자동화하고, 사고와 near miss에서 빠진 테스트를 보강한다.

테스트는 변경 전후 비교, 경계값, 의존성 실패, 데이터 호환성, 롤백 가능성도 다룬다. 테스트용 환경이 생산과 다르면 통과한 테스트가 production 위험을 보장하지 못할 수 있다. 설정·데이터·트래픽 특성을 현실에 가깝게 유지한다.

### 3. 카나리와 긴급 롤아웃

**카나리**는 소량의 트래픽이나 인스턴스에 변경을 먼저 적용하고, 나머지와 비교해 이상 여부를 판단하는 배포 방식이다.

1. 변경 전 기준선과 성공/중단 조건을 정한다.
2. 제한된 사용자·지역·인스턴스에서 변경을 실행한다.
3. 오류율·지연·자원·사용자 여정 등 적절한 신호를 대조군과 비교한다.
4. 이상이 없으면 점진적으로 확대하고, 악화하면 자동 또는 수동으로 중단·롤백한다.

카나리는 대표성을 갖는 트래픽, 충분한 관찰 시간, 올바른 대조군이 있어야 의미가 있다. 배포 직후의 일시적 변동과 실제 회귀를 구분하고, 영향을 받는 사용자의 중요한 지표를 측정한다. 안전한 긴급 롤아웃은 일반 절차를 무시하는 예외가 아니라, 제한된 범위·빠른 피드백·명확한 종료 조건을 갖춘 별도 경로다.

### 4. 재해 복구와 복원력 테스트

장애 복구 계획은 문서로 존재하는 것만으로 충분하지 않다. 실제로 복구 가능한지 정기적으로 시험해야 한다. 지역·존·의존성 장애를 가정하고 트래픽 전환, 용량 여유, 데이터 복구, 운영자 역할을 검증한다. 복구 연습 중 발견한 격차는 시스템 설계와 런북에 반영한다.

### 5. Client-Focused Change Supervision

변경 감시는 내부 구성 요소의 건강만 보는 것이 아니라 클라이언트가 경험하는 결과에 초점을 둔다. 핵심 사용자 여정(CUJ)의 성공·지연·오류가 변경 중 어떻게 달라졌는지 추적하면 내부 지표상 정상인 채 사용자 경험만 깨지는 문제도 찾을 수 있다. 효과적인 감독은 출시 전 준비, 단계적 실행, 지속적인 관측, 책임 있는 중단/복구, 사후 결과 검토가 연결된 과정이다.

### 6. Fault Injection Testing

전통적인 테스트는 예상한 경로와 장애만 확인하기 쉽다. Fault injection은 의존성 지연·실패, 프로세스 종료, 네트워크 문제, 용량 부족 등을 의도적으로 주입해 시스템이 실제 오류 상황에서 어떻게 반응하는지 확인한다.

- 왜 하는가: 실패 모드가 문서상 설계와 일치하는지, 격리·fallback·복구가 작동하는지 검증한다.
- 시작: 작은 비생산 환경과 명확한 가설·중단 조건으로 시작하고, 영향 범위를 통제한다.
- 인프라: 장애를 주입·관측·제거하는 도구와 안전장치가 필요하다.
- 의존성: 한 구성 요소의 실패가 상위·하위로 전파되는 방식을 함께 시험한다.
- 대규모 장애 모델: 단일 장애뿐 아니라 공통 원인, 여러 동시 실패, 복구 중 부하 같은 복합 상황을 고려한다.

이 테스트는 운영 환경의 모든 가능성을 증명하지 않는다. 모델이 현실을 충분히 반영하는지, 신호가 복구 여부를 판별하는지, 실험이 고객에게 위험을 주지 않는지 검토한다. chaos 실험은 목적 없는 무작위 파괴가 아니라 검증 가능한 가설에 기반해야 한다.

### 7. Formal Methods

Formal methods는 시스템의 상태와 속성을 수학적 모델로 표현해 특정 조건이 항상 성립하는지 분석하는 방법이다. 테스트가 선택된 입력·실행을 표본 조사한다면, 모델 검증은 모델의 상태 공간에서 불변식 위반이나 반례를 체계적으로 탐색한다. 모든 현실을 모델에 넣을 수는 없으므로 모델의 경계와 가정을 명시해야 한다.

사용 사례는 분산 프로토콜, 동시성, 안전 속성처럼 적은 결함도 큰 영향을 주는 영역이다. 모델 기반 접근은 설계 초기에 모호한 요구사항과 상호작용을 드러낸다. 자동화된 모델 체커는 상태 폭발에 직면할 수 있으며, 추상화·상태 축소·속성 선택이 중요하다. 정형 검증은 일반 테스트를 대체하기보다 검증하기 어려운 핵심 속성에 집중한다.

Google의 활용 사례가 주는 요지는 도구 자체보다 적절한 문제 선택이다. 모든 서비스에 형식 검증을 강제하기보다, 복잡한 프로토콜이나 안전 불변식처럼 비용 대비 효과가 큰 곳에서 전문가와 개발팀이 함께 적용한다.

### 8. Agentic Testing

에이전트 기반 테스트는 AI가 테스트 생성·실행·결과 분석을 돕는 가능성을 보여준다. 그러나 생성된 테스트가 실제 사용자 요구나 신뢰성 속성을 검증하는지는 사람이 확인해야 한다. 에이전트에게 주는 목표·권한·환경을 제한하고, 테스트 결과를 재현 가능하게 기록한다. AI가 만든 코드와 테스트를 서로 독립된 검증으로 간주하지 말고, 중요한 결과는 deterministic한 검사와 사람의 리뷰를 결합한다.
