# Google SRE Book v2 — Chapters 15–16

## Chapter 15. Capacity Planning

### 1. 용량 계획을 자동화하고도 계획해야 하는 이유

용량 계획은 미래 수요를 만족할 공급을 적시에 확보하면서 비용·성능·복원력의 균형을 맞추는 일이다. 자동 확장과 자원 할당 도구가 있어도 하드웨어·전력·공간·공급망·예산은 순간적으로 늘릴 수 없다. 자동화는 계획을 없애기보다 예측과 실행의 피드백 주기를 줄인다.

핵심은 “얼마나 필요한가”만이 아니라 수요의 불확실성, 장애 시 요구 용량, 자원 확보에 걸리는 시간, 다른 시스템과의 의존성을 함께 다루는 것이다.

### 2. 기본 개념과 수요 예측

- **수요(demand)**: 사용자 트래픽과 제품 기능이 요구하는 처리량·저장량·연산량.
- **공급(supply)**: 실제로 제공 가능한 CPU, 메모리, 저장소, 네트워크, 가속기 및 위치별 용량.
- **이용률(utilization)**: 공급 중 사용 중인 비율. 지나치게 낮으면 낭비, 지나치게 높으면 급증·장애 대응 여지가 줄어든다.
- **여유(headroom)**: 예상 오차·피크·장애 시 흡수력을 위해 남기는 여분.
- **리드 타임**: 물리적·재정적 공급을 확보하는 데 필요한 시간.

수요 예측은 과거 추세의 외삽만으로 충분하지 않다. 제품 출시, 고객 성장, 계절성, 가격 정책, 신규 지역, 모델·기능 변화 같은 사업 입력을 포함한다. 단일 숫자 대신 시나리오와 구간으로 불확실성을 표현한다. 수요가 예상보다 빨리 성장하거나 공급이 지연되는 경우의 계획도 마련한다.

### 3. 사업 중심 수요와 공급 계획

사업 계획을 기술 지표에 연결해야 한다. 사용자·요청·데이터 증가가 자원 소비로 어떻게 전환되는지 단위 경제성을 파악하고, 제품팀과 성장 가정을 맞춘다. 공급 측은 데이터센터·클러스터·랙·가속기 등 실제 공급 단위와 시간표를 반영한다. 서로 다른 지역·세대·구성의 용량을 단순 합산하지 말고, 제품이 실제 사용할 수 있는 용량인지 확인한다.

### 4. 복원력과 위험을 반영한 용량

정상 시 수요만 수용하는 용량은 장애 순간에 실패할 수 있다. 설계 목표는 어느 장애 영역이 사라져도 중요 트래픽을 처리할 수 있는지 명시해야 한다.

- **트래픽 요구사항 태깅**: 중요도와 우선순위로 부하를 분류해 부족 상황에 어떤 요청을 보존할지 정의한다.
- **용량 격리·실패 도메인**: 한 사용자·서비스·지역의 폭증이나 고장이 전체 자원을 잠식하지 않도록 경계를 둔다.
- **과부하 완화**: admission control, rate limit, 큐 제한, 부하 분산, 우선순위, load shedding을 조합한다.
- **계획된 정비·장애**: 용량을 빼는 작업은 다른 영역의 안전 여유를 계산하고, 동시 작업을 제한한다.
- **우아한 성능 저하**: 필수 기능을 우선 유지하고 비핵심 기능을 제한해 완전 장애를 피한다.

캐스케이드 실패를 막으려면 “평균 용량이 충분하다”보다 피크와 실패 후 복구 시의 동시 수요를 살펴야 한다. 의존 서비스가 장애 후 재시도 폭증을 겪으면 원래보다 더 큰 용량을 요구할 수도 있다.

### 5. 효율성·풀링·유휴 자원 회수

리소스 효율 개선은 새로운 용량을 확보하는 것과 같은 효과를 낼 수 있다. 공통 풀에서 자원을 공유하면 서비스별 피크가 엇갈리는 이점을 얻지만, 격리와 예약 보장이 약해질 수 있다. Flex/버스트 자원은 일시적 수요에 도움이 되지만, 중요한 SLO를 보장하는 기반 용량과 구분해야 한다.

“stranded capacity”는 전체로 보면 남아 있지만 위치·할당·제약 때문에 수요가 있는 곳에서 쓰지 못하는 용량이다. 자원 회수·재배치·세대 전환, 배치 크기 개선, 실제 워크로드 특성에 맞춘 인스턴스 선택으로 회수한다. 이용률만 높이는 것이 목표가 아니라 SLO를 지키면서 낭비를 줄이는 것이 목표다.

### 6. 용량 추정과 의존성 지도

서비스 단위의 부하 테스트·프로파일링을 통해 요청량당 CPU, 메모리, 저장소, 네트워크 사용을 추정한다. 실제 서비스 구성·데이터 크기·캐시 적중률과 차이가 없는지 확인한다. 전체 경로의 의존성 지도를 만들고 각 단계의 용량 한계와 고장 모드를 연결하면, 병목을 한 구성 요소만 늘려 해결하려는 오류를 줄인다.

병목은 시간에 따라 이동할 수 있다. 하나의 자원을 확장하면 다른 큐·네트워크·저장소가 다음 병목이 된다. 용량 변경 전후에 전체 경로 지표를 확인한다.

### 7. 변경과 지속 가능성

용량·구성 변경은 production 변경 관리의 일부다. 단계적으로 적용하고, 효과와 부작용을 관측하고, 안전한 되돌리기를 준비한다. 계획 가정은 주기적으로 재평가한다. 오래된 모델을 그대로 유지하면 제품 믹스나 하드웨어 세대 변화가 반영되지 않는다.

Google Meet의 COVID 시기 사례는 수요가 급격히 튀었을 때 용량·효율·우선순위·사업 대응을 함께 조정해야 함을 보여준다. AI 규모 확대 사례는 기존 공급 계획으로 설명되지 않는 가속기·전력 제약과 워크로드별 효율 차이를 강조한다. 수요를 무조건 수용하는 것 외에 요청 패턴·모델 선택·스케줄링을 통한 수요 형성도 고려해야 한다.

### 8. AI 용량의 추가 고려사항

AI 워크로드는 가속기 희소성, 모델 크기, 학습/추론의 상이한 패턴, 네트워크·메모리 병목, 에너지 소비를 포함한다. 중앙화된 fleet 관리와 workload 특화 스케줄러, 가속기 간 호환성(fungibility), 자동 자원 할당이 중요하다. 전력 제약이 있는 환경의 oversubscription은 계획된 정책과 품질 우선순위가 있어야 한다. 높은 이용률만 추구해 대기시간과 SLO를 훼손하지 않는다.

**용량 계획 체크리스트**

- 사업 성장 가정과 기술 자원 모델이 연결되어 있는가?
- 예측은 단일 수치가 아니라 불확실성과 공급 리드타임을 반영하는가?
- 장애·정비·피크를 견딜 용량과 우선순위가 정의되어 있는가?
- 숨은 병목 및 stranded capacity를 찾을 의존성 지도가 있는가?
- 효율 개선 후 SLO, 비용, 에너지 영향을 함께 검증하는가?

## Chapter 16. Data Management

### 1. 데이터는 신뢰성 설계의 중심

데이터 관리는 저장소의 가용성만이 아니라 무엇을 보존하고, 누가 접근하며, 언제 복구할 수 있고, 어떤 손실을 감수할 수 있는지 정하는 일이다. 기술적 복구 가능성과 법적·윤리적 허용 가능성은 별도로 검토해야 한다.

### 2. 법적·윤리적 고려와 분류

데이터의 수집·보관·처리는 관할권, 계약, 규제, 사용자 기대를 따른다. 필요 이상으로 수집하거나 무기한 보관하는 것은 위험을 키운다. Bigtable 보존 사례는 대규모 저장 기술이 가능하더라도 보존 기간과 삭제 정책이 제품·법률 요구에 맞아야 한다는 점을 보여준다.

윤리적 판단도 중요하다. 개인 데이터의 민감도, 사용 목적, 편향·오용 위험, 삭제 요청을 고려한다. 저장소를 다음과 같이 분류하면 보안·복구 정책을 차등 적용할 수 있다.

- 원본 데이터와 파생 데이터: 원본 삭제 후에도 복사본·집계·캐시가 남는지 추적한다.
- 식별 가능/비식별 데이터: 재식별 가능성을 포함해 민감도를 판단한다.
- 고가치 개인 데이터: 접근·감사·암호화·보존 통제를 강화한다.

### 3. 데이터 요구의 계층과 무결성

데이터 신뢰성에는 무결성, 기밀성, 가용성, 효율성이 서로 영향을 준다. 데이터가 빠르게 응답해도 틀리거나 오래된 값이라면 서비스는 신뢰할 수 없다. 복제 중 파일이 손상된 사례처럼, 복제 성공만으로 무결성이 보장되지는 않는다. 체크섬, 검증, 오류 탐지, 독립적 복구본이 필요하다.

계층적 데이터 요구를 정할 때는 업무상 중요도와 허용 가능한 손실을 데이터 집합별로 구분한다. 모든 데이터에 같은 비용의 보존·복구 수준을 적용하면 비용이 불필요하게 커지거나 중요한 데이터가 충분히 보호되지 않는다.

### 4. 보안·가용성·효율성

데이터 보안은 최소 권한, 암호화, 키 관리, 감사, 안전한 삭제, 격리를 포함한다. 가용성 설계는 장애 유형별로 데이터에 어떤 영향을 주는지 검토한다. 효율성은 비용과 성능뿐 아니라 복구 시간이 운영 목표를 만족하는지도 포함한다.

데이터 손실·손상의 대표 시나리오:

- 운영자 실수 또는 악의적 변경/삭제
- 애플리케이션 버그가 잘못된 데이터를 대량 기록
- 저장·복제 과정의 손상
- 하드웨어 고장
- 존·지역·전체 환경 장애

각 시나리오에 대해 탐지 방법, 영향 범위, 복구 가능한 시점, 책임자, 복구 테스트를 연결한다.

### 5. 데이터 SLO와 RPO/RTO/RWO

- **RPO (Recovery Point Objective)**: 장애 후 복구 시 허용 가능한 데이터 손실 시간/양.
- **RTO (Recovery Time Objective)**: 서비스/데이터를 복구해야 하는 목표 시간.
- **RWO (Recovery Workload Objective)**: 복구 시 감당해야 하는 작업량·복구 처리 역량의 목표. 복구가 시작돼도 backlog를 처리할 능력이 부족하면 정상화가 지연된다.

이 목표를 업무 영향과 연결하고, 서비스 수준 목표 및 데이터 보존 정책으로 구체화한다. 복제는 가용성을 높일 수 있지만 논리적 삭제나 잘못된 쓰기까지 복제할 수 있으므로 백업과 같은 의미가 아니다.

### 6. 복제, 백업, 스냅샷과 복구

- **복제**는 최신 상태를 다른 곳에 유지해 장애 전환을 돕는다. 원본의 손상이 복제본으로 전파될 수 있다.
- **백업**은 별도 복구 지점으로 보존해 논리적 오류·삭제에서 돌아갈 수 있게 한다.
- **스냅샷**은 특정 시점의 저장소 상태를 빠르게 보존하는 메커니즘이다. 구현 방식에 따라 독립 백업과 동일한 보호를 보장하지 않는다.
- **Point-in-time recovery**는 로그/변경 이력을 사용해 특정 시점으로 복원한다.
- **전체/증분/차등 백업**은 보존량·복구 복잡도·복구 시간의 다른 절충을 제공한다.
- **스마트/단순 백업**은 저장·중복 제거 효율과 구현·검증 복잡도의 균형을 따진다.

백업의 존재보다 실제 restore 성공이 중요하다. 정기 복구 시험으로 백업이 읽히는지, 필요한 키·설정·의존성이 있는지, 복구 시간이 목표에 맞는지 확인한다.

### 7. 복구 프레임워크

1. 업무 영향과 복구 우선순위를 정한다.
2. 데이터 원천·복사본·파생본을 목록화하고 분류한다.
3. 각 데이터 클래스에 RPO/RTO/RWO와 SLO를 설정한다.
4. 복제·백업·보존·접근 제어를 구성한다.
5. 실제 장애를 가정해 restore와 서비스 재개를 시험한다.
6. 절차·담당자·승인·의사소통을 문서화하고 변경에 맞춰 갱신한다.
7. 사고와 테스트 결과를 반영해 정책과 자동화를 개선한다.

복구 정책은 기술 절차만이 아니다. 누가 복구를 선언하는지, 어느 지점을 선택하는지, 다운스트림 데이터를 어떻게 조정하는지, 고객에게 어떻게 알리는지 포함한다. **핵심 원칙은 백업을 검증하고, 삭제·손상·지역 장애를 구별해 각기 다른 복구 방법을 갖추는 것**이다.
