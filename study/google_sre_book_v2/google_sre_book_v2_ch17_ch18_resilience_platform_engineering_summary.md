# Google SRE Book v2 — Chapters 17–18

> 학습용 상세 정리. 복원력 원칙과 플랫폼 설계의 연결을 중심으로 정리했다.

## Chapter 17. Designing for Resilience

### 1. 신뢰성 목표를 넘어 복원력으로

복원력은 장애가 전혀 없다는 뜻이 아니라 변화·오류·공격·수요 급증 속에서도 핵심 기능을 유지하고 회복하는 능력이다. 시스템 규모와 상호의존성이 커지면 과거에 드물던 조합이 현실이 되고, 한 서비스의 국소 문제도 연쇄 장애가 될 수 있다. 그러므로 개별 구성 요소의 성공 확률뿐 아니라 사용자 여정과 전체 시스템의 행동을 설계한다.

사용자는 내부 구성 요소가 건강한지보다 필요한 작업이 성공하는지, 얼마나 빨리 복구되는지 경험한다. 기대 수준과 위험 수용도는 서비스의 중요도·비용·사용자 맥락에 맞게 정한다.

### 2. 복원력의 조직적 토대

Google의 신뢰성 원칙은 기술 규칙만으로 작동하지 않는다. 일관된 기본 플랫폼, 표준화된 방식, 책임 있는 리스크 관리, 리더십의 지원, 팀 간 협력이 함께 있어야 한다.

- **기술 집행**: 기본 설정과 도구가 안전한 선택을 쉽게 만든다.
- **균일성**: 공통 배포·관측·용량 관리 방식이 운영 지식과 대응을 재사용하게 한다.
- **위험 관리**: 오류 예산·위험 허용도·완화 계획으로 속도와 안정성을 조율한다.
- **팀/리더십**: 명확한 소유권과 투자 결정으로 신뢰성 개선을 지속한다.

표준화는 모든 서비스를 동일하게 만드는 것이 아니라, 공통 실패 방지 원칙을 기본 제공하고 특별한 요구는 명시적으로 다루는 것이다.

### 3. 변화 관리와 심층 방어

변경은 장애의 주요 원인이므로 변경을 없애기보다 위험을 통제한다.

- 점진적 rollout과 비교 측정으로 영향 범위를 제한한다.
- 동시 변경 수를 제한해 원인 추적과 격리를 쉽게 한다.
- 변경을 지속적으로 감독하고 이상 시 빠르게 중단·완화한다.
- 안전한 완화책을 준비하고 실제로 사용할 수 있는지 연습한다.
- 위험 허용도와 오류 예산을 이용해 변경 속도를 조절한다.

단일 보호책을 믿지 않고 서로 독립된 방어 계층을 둔다. 예컨대 검증·단계 배포·격리·모니터링·롤백이 함께 작동해야 한다. 각 방어가 같은 공통 원인에 동시에 실패하지 않는지 살핀다.

### 4. 의존성 관리

의존성을 목록화하는 것을 넘어 표현하고, 통제하고, 실패를 모델링해야 한다. 서비스 그래프에는 직접 호출뿐 아니라 데이터·제어 경로, 운영 도구, 외부 공급자도 포함될 수 있다. 의존성이 실패했을 때 상위 서비스가 무엇을 유지할지 정의한다.

- 중요한 의존성의 실패 확률·복구 시간·영향을 이해한다.
- timeout, retry, circuit breaker, bulkhead를 올바르게 설정한다.
- 대체 경로(fallback)는 단순히 존재하는 것이 아니라 실제로 독립적이며 감당 가능한지 검증한다.
- 상위 서비스가 하위 의존성을 과부하시키지 않도록 보호한다.

### 5. 실패 도메인과 데이터 손실 예방

실패 도메인에는 프로세스·머신·랙·존·지역·제어 평면·공급자 등이 있다. 서비스의 중요도와 비용에 맞춰 분산 위치를 정하고, 실제로 독립적인지 확인한다. 두 복제본이 같은 설정·제어 시스템·자격 증명에 의존한다면 독립성이 낮을 수 있다.

데이터 손실을 막으려면 삭제/수정이 복제되는 상황을 고려하고, 취소 가능한 삭제(undelete), 보호된 백업, 독립된 복구 경로를 둔다. 데이터 복구 속도도 복원력이다.

### 6. 과부하와 연쇄 장애

과부하는 시스템의 처리 능력을 넘어서는 입력에서 발생하며, 대기열·재시도·자원 고갈을 통해 주변으로 번진다. 서버 측 제한과 클라이언트 측 동작을 함께 설계한다.

- 서버: admission control, 큐 상한, 우선순위, 부하 차단, 격리.
- 클라이언트: deadline, 지터가 있는 backoff, 재시도 예산, 요청 중복 억제.
- 시스템: 과부하가 생겼을 때 핵심 요청을 보존하고 비핵심 기능을 graceful degradation한다.
- 완화책: 운영자가 실제 상황에서 빠르게 판단할 수 있는 명확한 지표·절차·도구를 제공한다.

무제한 재시도와 큐는 문제를 늦출 뿐 아니라 더 큰 장애를 만든다. 부하를 낮추는 조치와 회복 시 갑작스러운 트래픽 재개도 계획한다.

### 7. 입력 검증과 운영 모드

외부 또는 내부 입력은 잘못된 형식·크기·순서·빈도일 수 있다. 입력 검증은 오류를 경계에서 차단하고, 오류 결과가 서비스·데이터에 미칠 영향을 제한한다. 단순히 거부하는 것 외에도 검증 실패가 운영자에게 유용하게 드러나는지 확인한다.

일상 운영, 성능 저하, 긴급 대응, 복구 등 상황별 모드를 정의하면 시스템이 압박 중에도 일관된 행동을 할 수 있다. 긴급 모드는 별도 권한·절차·검증이 필요하다.

### 8. 자격 검증과 Shift Left

변경·새 하드웨어·새 의존성을 production 이전에 현실적인 환경에서 검증한다. 작은 테스트 환경이 실제 부하·구성·데이터를 반영하지 못하면 잘못된 자신감을 줄 수 있다. 위험 신호를 개발 초기로 이동시키되, 검증 책임을 개별 개발자에게 무한히 전가하지 않는다.

개발자에게는 안전한 기본값과 테스트 가능한 인터페이스를 제공하고, 대응자에게는 영향·완화·복구 경로를 제공한다. 리더는 위험을 감수하는 명시적 의사결정과 개선 투자에 책임을 진다. CUJ(Response CUJs)을 활용해 장애 대응이 실제 사용자 여정을 회복하는지 평가한다. 교육·훈련은 역할에 맞게 지속한다.

**복원력 리뷰 질문**

- 핵심 사용자 여정과 허용 가능한 저하 상태가 정의됐는가?
- 실패 영역·공통 원인·복구 경로를 모델링했는가?
- 과부하 때 재시도·큐가 장애를 증폭시키지 않는가?
- 운영자가 쓸 완화책을 테스트·훈련했는가?
- 데이터 삭제와 복구가 복제와 독립적으로 검증되는가?

## Chapter 18. Platform Engineering in SRE

### 1. 플랫폼은 내부 제품이자 정원

플랫폼은 개발·운영 팀이 서비스를 만들고 운영하는 데 사용하는 공통 기능, 추상화, 정책, 도구의 집합이다. 목표는 중앙팀이 모든 결정을 대신하는 것이 아니라, 반복되는 복잡성을 없애고 좋은 운영 선택을 기본값으로 만드는 것이다.

플랫폼을 정원처럼 보면, 완성 후 방치되는 산출물이 아니라 계속 돌보고 가지치기하는 생태계다. 사용자의 요구가 변하고 기술이 진화하므로 피드백·유지보수·폐기 계획이 필요하다. 플랫폼은 내부 고객의 생산성·안전·신뢰성을 함께 책임진다.

### 2. 복잡성, 추상화, 결합도

플랫폼은 세부사항을 추상화해 인지 부담을 낮추지만, 잘못된 추상화는 필요한 제어를 감추거나 특수 상황을 어렵게 만든다. 추상화는 단순함과 표현력 사이의 선택이다.

- 강한 결합은 여러 구성 요소의 변경을 동시에 요구하고 장애를 전파한다.
- 약한 결합과 명확한 인터페이스는 팀이 독립적으로 변화할 여지를 준다.
- 플랫폼 API는 사용자의 의도·책임·실패 의미를 분명히 표현해야 한다.
- 내부 구현을 모두 노출하면 플랫폼이 운영 복잡성을 사용자에게 다시 떠넘긴다.

### 3. 제어 이론과 시스템 관점

조직은 복잡한 시스템이다. 중앙 제어자가 모든 상태를 알 수 있다고 가정하면 실패한다. 플랫폼은 사용자의 결과를 감지하고, 정책·가드레일을 제공하며, 실제 효과를 피드백 받는 제어 루프를 가져야 한다.

직접 제어(명령·승인)와 간접 제어(기본값·API·정책·인센티브)의 균형을 선택한다. 직접 통제는 안전성을 높일 수 있지만 병목과 맥락 손실을 만들 수 있다. 간접 방식은 자율성을 키우지만 결과를 관측하고 잘못된 경로를 수정할 피드백이 필요하다.

### 4. 선택지·가드레일·예외

옵션이 많으면 선택의 자유가 늘어나는 동시에 인지 부담과 조합 수가 급증한다. 좋은 플랫폼은 안전하고 흔한 경로를 쉽게 하고 위험한 선택은 의도적으로 어렵게 만든다.

- **기본 경로**: 합리적인 보안·관측·배포·용량 설정을 포함한다.
- **가드레일**: 위험한 상태를 막거나 조기 경고한다.
- **예외 경로**: 정당한 특수 요구를 처리하되, 이유·소유자·만료·위험을 기록한다.
- **피드백**: 예외가 반복되면 플랫폼의 일반 기능 부족인지 검토한다.

예외를 무조건 금지하면 비공식 우회로를 만들고, 무제한 허용하면 표준화가 사라진다. 운영 가능한 정책과 투명한 심의가 필요하다.

### 5. 플랫폼에서 생태계로

조직 내 여러 플랫폼이 서로 얽히면 단일 제품보다 생태계가 된다. 플랫폼 간 계약·소유권·버전·관측 가능성을 다뤄야 한다. Shift left가 모든 책임을 개발자에게 이동시켜 복잡성을 키울 수 있다면, shift down은 관리형 플랫폼으로 반복 부담을 아래 계층에 흡수한다.

이 방식은 개발자가 인프라 전체의 전문가가 되지 않아도 신뢰성·보안 기본값을 따르도록 한다. 다만 “플랫폼 팀이 알아서 한다”는 블랙박스를 만들지 않도록 서비스 소유자에게 필요한 결과와 상태 정보를 제공한다.

### 6. 플랫폼 효과 측정

사용량 자체는 성공 지표가 아니다. 다음을 함께 측정한다.

- 개발자가 핵심 기능에 도달하는 시간과 출시 준비 기간
- 표준 플랫폼 채택률과 예외 사유
- 배포 실패·복구 시간·보안/신뢰성 기본 요구 준수
- 운영 부담과 반복 작업 감소
- 내부 사용자의 만족·지원 요청·우회 사용

### 7. 플랫폼을 상태 기계로 바라보기

플랫폼의 배포·구성 흐름을 상태 기계처럼 모델링하면 허용 상태, 전이, 실패 복구를 명시할 수 있다. 각 상태가 읽기 쉽고(introspective), 사용자가 현재 상태·정책 위반·다음 조치를 이해할 수 있어야 한다. 교정(remediation)은 안전하고 반복 가능해야 하며, 자동 수정이 위험한 경우 명시적인 사용자 개입 경로를 둔다.

Greenfield 환경에서는 표준 구조를 처음부터 적용하기 쉽지만, Brownfield에서는 기존 제약·데이터·팀 습관과의 점진적 이행이 중요하다. 한 번에 재작성하기보다 병행·호환·마이그레이션 경로를 설계한다.

**플랫폼 설계 점검**

- 내부 고객의 실제 문제를 확인했는가?
- 추상화가 복잡성을 제거했는지, 다른 곳으로 숨겼는지 측정하는가?
- 기본 경로는 안전하고 예외는 투명하게 관리되는가?
- 플랫폼의 현재 상태와 복구 방법이 사용자에게 보이는가?
- 사용자의 피드백과 운영 데이터에 따라 플랫폼을 계속 정원처럼 돌보는가?
