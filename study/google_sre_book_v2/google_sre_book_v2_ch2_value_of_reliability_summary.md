# 2장 요약 - 신뢰성의 가치

> 원제: *The Value of Reliability*

## 한눈에 보기

신뢰성은 기술 비용이 아니라 **사용자 신뢰, 매출, 개발 속도, 조직 효율을 좌우하는 사업 투자**다. SRE는 운영을 자동화·표준화해 서비스 규모보다 운영 비용이 느리게 증가하도록 만들고, 적정 신뢰성과 기능 출시 속도 사이의 균형을 의도적으로 관리한다.

핵심은 100% 가용성을 목표로 삼는 것이 아니다. 사용자 기대와 사업 목적에 맞는 신뢰성 목표를 정하고, 그 안에서 위험과 혁신을 균형 있게 선택하는 것이다.

---

## 1. 왜 SRE인가

전통적인 개발-운영 분리는 코드가 운영팀에 일방적으로 넘어가고, 장애 시 책임 공방이 생기기 쉬운 구조다. 운영 인력이 반복 작업을 늘려가며 성장에 대응하면 비용과 피로가 함께 커진다.

SRE는 이를 다음과 같이 바꾼다.

| 전통적 운영 중심 | SRE 접근 |
| --- | --- |
| 안정성에 치우쳐 변경 속도를 희생하기 쉬움 | 오류 예산으로 신뢰성과 기능 투자를 함께 조절 |
| 반복 수작업을 인력으로 흡수 | 자동화·표준화로 제거 |
| 개발과 운영의 목표가 분리됨 | 공통 목표와 공동 책임을 형성 |
| 개별 팀의 국소적 해결 | 공통 플랫폼과 도구를 통해 개선 효과를 공유 |

SRE는 운영 관리를 사람의 문제보다 소프트웨어 문제로 다룬다. 그 결과 대규모 운영의 신뢰성·가용성·확장성을 별도 전문 영역으로 관리할 수 있다.

## 2. 핵심 경제 논리: 서브리니어 스케일링

SRE가 제공하는 중요한 사업 가치는 **서비스 규모보다 운영 비용과 인력 증가가 느린 구조**다. 이를 서브리니어(sublinear) 스케일링이라고 부른다.

```text
서비스 규모 증가
  ├─ 사람을 늘려 수작업을 처리하면 → 운영 비용도 비슷한 속도로 증가
  └─ 자동화·표준화·공유 플랫폼을 만들면 → 추가 서비스의 운영 한계비용이 낮아짐
```

이를 가능하게 하는 수단은 다음과 같다.

- **Toil 제거**: 수동·반복·자동화 가능·전술적이며 오래 남는 가치가 적은 일을 찾아 코드로 대체한다.
- **공유 기반**: 여러 서비스가 공통으로 쓰는 로드밸런싱, 배포, 관측성 같은 기능을 중앙 플랫폼으로 제공한다.
- **표준화**: 잘 검증된 실무를 팀마다 다시 발명하지 않도록 한다.
- **오류 예산**: 신뢰성과 기능 출시를 같은 목표 체계 안에서 조율한다.

자동화는 단순한 인건비 절감이 아니다. 사람의 창의성과 문제 해결 능력을 반복 작업이 아닌 더 높은 가치의 엔지니어링에 쓰게 하는 투자다.

## 3. 이해관계자별 가치

### 고객

- 서비스가 사용할 수 있고, 빠르며, 정확하게 동작하는 것은 다른 모든 기능의 전제다.
- 고객은 명시적 SLO를 몰라도 일정 수준의 서비스 품질을 기대한다. 기대가 깨지면 만족도, 추천 의향, 지출과 재방문에 영향을 준다.
- 목표는 무조건적인 100% 가용성이 아니다. 과도한 신뢰성 추구는 비용을 높이고 기능 출시를 늦출 수 있다. 사용자 경험 전체를 최대화하는 적정 수준을 선택해야 한다.

### 재무 책임자와 경영진

- 코드와 자동화는 반복 실행의 추가 비용이 낮아 성장의 레버리지로 작동한다.
- 공유 플랫폼에 대한 한 번의 개선이 여러 제품에 동시에 적용되어 투자 효과가 누적된다.
- 신뢰성은 매출 손실·복구 비용·이탈·평판 손상 같은 비용을 낮추고, 성장에 필요한 운영 효율을 높인다.

### 제품·개발·인프라 등 내부 기술팀

- SLO 같은 객관적 지표가 사업 요구를 기술 목표로 바꿔 팀 간 대화를 구체화한다.
- SRE의 생산 환경 전문성이 개발팀의 인지 부하를 줄여, 팀이 비즈니스 로직과 제품 품질에 더 집중하게 한다.
- 공통 목표와 명확한 위험 설명은 출시 속도와 장애 심각도를 함께 개선한다.

### 조직 문화와 SRE 팀

- 비난 없는 회고와 심리적 안전감은 장애에서 학습하고 문제를 조기에 드러내는 기반이다.
- 신뢰성 의사결정은 데이터와 리더십의 지지가 필요하다.
- Toil을 줄이면 야간 호출, 반복 복구, 번아웃이 감소하고 팀의 사기·생산성·지속 가능성이 높아진다.
- 서비스가 지속적으로 목표를 지키지 못해 온콜 부담을 해치면, 개발팀과 책임을 다시 정렬하는 장치가 필요하다.

## 4. 신뢰성이 부족할 때의 비용

장애 비용은 단순한 ‘장애 시간 × 시간당 매출’보다 훨씬 넓다.

| 비용 유형 | 내용 |
| --- | --- |
| **직접 비용** | 판매·거래 손실, 복구 인력과 외부 비용, 계약상 보상 |
| **기회비용** | 엔지니어가 기능 개발을 멈추고 대응·복구에 투입됨 |
| **고객 이탈과 평판** | 고객이 경쟁 서비스로 옮기거나 장기 신뢰가 훼손됨 |
| **증가한 Toil** | 같은 수동 복구와 임시 조치를 반복하며 오류 가능성과 피로가 증가 |
| **속도 저하** | 불안정한 시스템 탓에 배포·실험·기능 개발이 느려짐 |
| **사후 보강 비용** | 출시 후 설계·테스트·관측성을 덧붙이는 비용이 초기에 설계하는 것보다 큼 |
| **기술 부채의 누적** | 작은 우회책이 복잡성과 변경 위험을 키워 장기적으로 시스템을 약화 |

특히 장애의 관리 비용은 파급 효과가 크다. 한 시간의 서비스 중단이 조사, 의사소통, 복구, 고객 대응, 후속 작업까지 포함하면 훨씬 더 많은 엔지니어링 시간을 소비할 수 있다.

## 5. 시스템 노화와 기술 부채

시스템은 변화하지 않을 수 없으며, 변화에는 실패와 복구가 따른다. 문제가 생길 때마다 임시 수동 해결책만 추가하면 시스템은 서서히 노화한다.

- 수동 우회가 늘어난다.
- 작은 변경도 예상치 못한 실패를 낸다.
- 엔지니어는 예방적 개선보다 늘어난 운영 부담을 처리하느라 바빠진다.
- 결국 대규모 정비가 필요해지고, 그 비용은 훨씬 커진다.

따라서 신뢰성 투자는 장애 후의 미관 개선이 아니라, 기술 부채가 운영 위험으로 변하기 전에 갚는 일이다.

## 6. 조직 단계에 따른 SRE 적용

### 초기·소규모 조직

처음부터 큰 SRE 조직을 만들 필요는 없다. 비교적 적은 비용으로 다음 기반을 우선할 수 있다.

- 자동화된 단위·통합 테스트: 버그를 개발자 환경에서 잡을수록 비용이 낮다.
- 자동화된 CI/CD: 빌드부터 배포까지를 반복 가능하게 만든다.
- 관측성: 사용자 경험 악화를 반영하고 실제 조치로 이어질 알림을 설계한다.
- 인시던트 대응 프로세스: 위기 때 역할·소통·복구 순서를 정한다.
- 설계 검토: 출시 전에 복구성, 의존성, 용량, 운영 가능성을 검토한다.

### 성장·성숙 조직

규모가 커지면 개별 서비스 개선을 넘어 조직 단위의 문제가 중요해진다.

- 전략적 엔지니어링 의사결정을 신뢰성 데이터로 뒷받침한다.
- 오래된 시스템의 복잡성과 의존성을 관리한다.
- 대규모 장애에서 빠르고 일관되게 대응할 수 있는 체계를 갖춘다.
- 여러 팀이 함께 쓸 중앙 도구·플랫폼을 만들어 공통 문제를 한 번에 해결한다.

## 7. SRE 도입 전 판단할 질문

- 이 서비스가 멈추거나 느려지면 사용자·매출·내부 업무에 어떤 피해가 생기는가?
- 요청이나 구매가 영구히 유실되는가, 아니면 나중에 재시도할 수 있는가?
- 수요가 급증하는 특정 시간대나 계절이 있는가?
- 고객이 기대하는 가용성·지연 시간·정확성은 무엇인가?
- 현재 반복 수작업과 온콜 부담은 어느 정도이며, 무엇을 먼저 자동화할 수 있는가?
- 장애의 직접 비용뿐 아니라 기회비용·평판·기술 부채를 포함해 측정하고 있는가?
- 리더십은 데이터 기반의 신뢰성 투자와 필요한 기능 출시 조절을 지지하는가?

## 핵심 결론

신뢰성은 기능 개발의 반대편에 있는 비용 항목이 아니다. **사용자 신뢰를 보호하고, 개발 속도를 지속 가능하게 만들며, 성장 시 운영 비용의 폭증을 막는 사업 역량**이다. SRE의 가치는 고장 나지 않은 시간을 세기보다, 자동화·표준화·명확한 목표를 통해 조직이 더 적은 운영 부담으로 더 안전하게 변화하도록 만드는 데 있다.
