# 8장 요약 - 서비스 수준 목표(SLO)

> 원제: *Service Level Objectives*

## 한눈에 보기

SLO는 사용자가 체감하는 신뢰성 수준을 명시하고, 기능 출시와 안정성 개선의 우선순위를 함께 정하는 운영 도구다. SLO 자체가 목적이 아니라 실제 사용자 경험을 측정하고 위험과 투자 결정을 돕는 데 목적이 있다.

## 핵심 개념

| 용어 | 의미 |
|---|---|
| Metric | 시스템 또는 사용자 경험을 나타내는 측정값 |
| SLI | 서비스의 좋고 나쁜 결과를 수치로 표현하는 지표 |
| SLO | SLI에 대해 정한 목표치와 측정 기간 |
| SLA | 목표 미달 시 책임이나 보상 조건을 포함하는 대외 합의 |
| 오류 예산 | SLO에서 허용하는 실패의 양 |
| 소진율 | 오류 예산이 허용 속도보다 얼마나 빠르게 줄어드는지 나타내는 비율 |
| CUJ | 사용자가 목표를 달성하기 위해 수행하는 핵심 작업 흐름 |

## SLI와 SLO를 정하는 방법

- 사용자가 하려는 작업과 성공 기준부터 정의한다.
- 내부 자원 상태보다 가용성, 지연 시간, 정확성, 작업 완료 등 사용자 결과를 측정한다.
- 중요한 서비스와 여정의 소수 지표부터 시작해 데이터를 보며 다듬는다.
- 목표는 무조건 높게 잡지 않는다. 사용자 기대, 장애 피해, 구현·운영 비용, 출시 속도를 고려한다.
- 내부 SLO는 외부 SLA보다 여유를 두어 문제를 먼저 감지하고 대응할 수 있게 한다.

## 오류 예산으로 위험과 출시를 조율

오류 예산은 안정성과 기능 개발을 공동 목표 아래 놓는다. 예산이 충분하면 합의한 위험 한도 안에서 변경을 진행하고, 빠르게 소진되면 위험한 변경을 줄이며 신뢰성 개선에 집중한다. 소진율 경보는 예산이 위험한 속도로 줄 때 대응을 돕는다. 경보는 모든 위반에 무조건 호출을 보내기보다 사용자 영향과 대응 시간을 반영해야 한다.

## 도입 시 흔한 함정

- CPU 같은 내부 지표만 측정해 실제 사용자 실패를 놓친다.
- 모든 API와 고객에 처음부터 너무 많은 SLO를 만든다.
- 목표를 정한 뒤 실제 경험을 보고 갱신하지 않는다.
- 의존 서비스와 조직 간 목표가 충돌하는데도 개별 팀 지표만 본다.
- 오류 예산을 팀을 평가하거나 처벌하는 점수로 사용한다.
- 문서 작성 자체를 성과로 보고 배포·알림·우선순위 결정에 활용하지 않는다.

## 핵심 사용자 여정과 고객별 SLO

단일 서비스 지표는 로그인부터 검색 결과 확인까지 이어지는 전체 경험을 설명하지 못할 수 있다. CUJ를 정의하고 각 단계의 성공, 정확성, 지연을 측정하면 백엔드가 정상이어도 사용자 작업이 실패하는 문제를 발견할 수 있다.

고객마다 중요한 워크로드가 다르면 고객별 SLO를 둘 수 있지만, 지나친 세분화는 데이터와 경보를 폭증시킨다. 중요한 고객과 작업에 범위를 제한하고, 고객이 중요하게 보는 결과 또는 신뢰할 만한 대리 지표를 사용한다. 워크로드 메타데이터와 경보의 정확성도 지속적으로 관리한다.

## 암묵적·클라이언트 측 SLO

- 공식 목표가 없어도 사용자는 반복적으로 경험한 품질을 기대치로 삼는다. 제공 품질을 크게 낮추면 기대 변화에 대해 설명해야 한다.
- 클라이언트 지표는 네트워크, 기기, 앱 렌더링 등 서버 지표가 놓치는 체감 성능을 측정한다.
- 비동기 흐름, 잡음, 표본 부족, 분모 정의 등으로 해석이 어려우므로 지표 정의를 표준화하고 측정 불확실성을 고려한다.

## 도구와 운영

공통 SLO 저장소와 도구는 지표, 목표, 담당자, 경보를 일관되게 관리하게 해 준다. 각 팀이 별도 체계를 만들면 운영과 정의가 분산되므로 공통 기반과 자율성의 균형이 필요하다. 다중 소진율 경보는 긴급도에 맞는 대응을 돕는다. 저트래픽 서비스는 몇 번의 실패로 비율이 크게 흔들리므로 표본 크기와 통계적 불확실성을 고려해야 한다. 서비스·팀·CUJ 단위로 SLO를 계층화하면 사용자 영향의 경로를 파악하기 쉽다.

## 실무 적용 순서

1. 중요한 사용자 작업 또는 CUJ를 고른다.
2. 성공·실패와 체감 지연을 정의한다.
3. 초기 SLI, SLO, 측정 기간을 정한다.
4. 오류 예산과 소진율 경보를 연결한다.
5. 배포와 장애 대응에서 목표가 실제 결정에 쓰이는지 확인한다.
6. 데이터와 사용자 피드백을 바탕으로 반복 조정한다.

## 핵심 결론

SLO는 신뢰성을 숫자로 꾸미는 일이 아니라, 사용자 경험을 기준으로 허용할 위험과 개선 우선순위를 결정하는 장치다. 의미 있는 목표 몇 개로 시작하고 오류 예산을 팀 간 공동 의사결정에 연결해야 한다.
