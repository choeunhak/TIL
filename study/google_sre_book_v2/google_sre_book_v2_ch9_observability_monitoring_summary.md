# 9장 요약 - 관측성과 모니터링

> 원제: *Observability and Monitoring*

## 한눈에 보기

복잡한 서비스의 문제를 해결하려면 미리 만든 대시보드와 임계치만으로는 부족하다. 메트릭, 로그, 트레이스, 프로파일링 등 여러 신호를 연결해 시스템 상태와 사용자 경험을 탐색할 수 있어야 한다. 관측성은 문제 감지에서 원인 조사, 안전한 변경, 자동 완화까지 지원한다.

## 모니터링에서 관측성으로

전통적인 모니터링은 예상된 문제를 정적 대시보드와 임계치로 감지하는 데 유용하지만, 복잡한 분산 시스템에서는 예상하지 못한 장애를 설명하기 어렵다. 관측성은 여러 신호와 맥락을 연결해 새로운 질문도 탐색할 수 있게 한다.

- **시계열 메트릭**: 시간에 따른 오류율, 지연, 자원 사용량
- **로그**: 시점별 사건의 상세 기록
- **분산 트레이스**: 요청이 여러 서비스로 흐르는 경로와 지연
- **연속 프로파일링**: 코드 실행과 자원 소비의 병목
- **토폴로지·자산 정보**: 서비스, 의존 관계, 담당자, 환경

공통 요청·배포·사용자 여정 식별자로 신호를 연결하면 여러 시스템에 걸쳐 원인을 조사하기 쉬워진다.

## 운영을 돕는 대시보드, 경보, 완화

- 공통 라이브러리와 플랫폼이 기본 대시보드를 제공하면 중복 제작과 유지 부담을 줄인다.
- 고정 임계치가 계절성이나 서비스별 차이를 놓칠 수 있으므로, 통계·머신러닝을 이용해 기준선과 유의미한 변화를 감지한다.
- 경보는 사용자 영향과 실제 조치에 연결되어야 한다.
- 오류·지연이 배포 직후 증가하면 자동 중단이나 롤백으로 완화할 수 있다. 자동 조치에는 검증과 되돌리기 경로가 필요하다.

## 텔레메트리의 두 가지 경로

| 구분 | 고가용성 텔레메트리 | 분석 텔레메트리 |
|---|---|---|
| 목적 | 즉시 감지·대응·제어 | 추세·용량 계획·과거 분석 |
| 우선순위 | 낮은 지연, 처리량, 신뢰성 | 데이터 완전성, 큰 저장 용량, 낮은 비용 |
| 예시 | 경보, 장애 감지, 프로브, 제어 루프 | 성능 분석, 과거 장애 조사, 감사 |

두 경로는 요구 사항이 다르다. 장애 때 관측 시스템이 서비스와 함께 멈추지 않도록 즉시 대응 경로를 독립적으로 설계하고, 사용자에게는 가능하면 공통 인터페이스를 제공한다.

## 표준화, OpenTelemetry, eBPF

관측 플랫폼은 이식성, 비용, 데이터 양, 통합성, 마이그레이션 비용을 함께 고려해 선택한다. OpenTelemetry(OTel)는 특정 업체에 종속되지 않는 텔레메트리 수집·전달 표준과 도구를 제공한다. 공통 식별자와 런타임·코드 출처 정보는 신호의 원인과 경로를 연결하는 데 도움을 준다. eBPF는 애플리케이션 변경을 최소화하면서 커널·네트워크 수준 신호를 관찰할 수 있는 방법이다.

AI 시스템에는 모델 호출과 에이전트 단계, 입력·출력, 비용 등 기존 요청 트레이스에 없는 관측 요소도 필요하다.

## 클라이언트 측 텔레메트리

서버가 정상이어도 사용자는 앱 시작 지연, 렌더링 문제, 불안정한 네트워크, 기기별 오류를 겪을 수 있다. 클라이언트 관측은 체감 지연과 숨은 오류를 찾아내고, 배포의 실제 영향을 확인하게 한다.

모바일·브라우저의 연결 단절, 업로드 버퍼링, 기기 저장 공간, 타임스탬프와 데이터 손실을 고려한다. 표본 탈락이 분석을 편향시키지 않는지 모니터링하고, 수집이 사용자 경험과 배터리에 주는 비용을 제한한다. 개인정보와 민감 데이터는 접근·암호화·보존 정책을 적용한다.

## 고객 중심 모니터링과 CUJ

사용자가 목표를 달성했는지 추적하기 위해 핵심 사용자 여정(CUJ)을 정의한다. 각 단계의 기능 성공 조건과 지연·가용성 요구를 연결하고, CUJ 식별자를 로그·메트릭·트레이스에 전파한다. 배포 전후 CUJ 지표를 자동 비교해 악화 시 변경을 중단하거나 되돌리는 방어 체계를 만든다. 여러 팀 소유의 서비스를 연결할 공통 정의와 인프라가 필요하다.

## 데이터 보존과 보안

모든 원본 텔레메트리를 오래 보관하면 비용과 위험이 커진다. 데이터 종류별 저장 매체, 기간, 샘플링, 집계 수준을 정하고 필요하면 집계 데이터를 미리 계산한다.

- 필요한 최소 데이터만 수집하고 민감도에 따라 분류한다.
- 최소 권한 접근 제어, 전송·저장 암호화, 지역별 저장 요건을 적용한다.
- 삭제 요청과 보존 기한을 관리한다.
- 로그·트레이스에 고객 입력이나 개인정보가 포함되는지 확인한다.
- 디버그 엔드포인트와 수집기 접근을 제한하고, 데이터 결합에 따른 과도한 노출을 막는다.

## 통계 기반 알림과 의존성 SLO

고정된 오류 건수만으로 경보를 만들면 트래픽 규모에 따라 과민하거나 늦을 수 있다. 이항분포와 신뢰구간을 활용하면 실패율이 우연한 변동인지 실제 악화인지 구분하는 데 도움이 된다. 지연은 유사한 요청 집단의 기준선과 비교해 상대적 회귀를 찾을 수 있다.

여러 서비스를 순차 호출하면 전체 성공률은 각 의존성의 성공률에 영향을 받는다. 병렬 요청이나 헤징은 가용성을 높일 수 있지만 부하와 비용을 키운다. 이런 계산은 독립 장애를 가정하므로, 공통 데이터베이스나 네트워크 같은 상관 장애 요인도 함께 살핀다.

## AI 활용

AI는 이상 징후 탐지, 로그 패턴 분석, 고객 피드백 분류, 반복 운영 작업 감소에 도움을 줄 수 있다. 결과를 조사 단서로 활용하되, 데이터 품질과 오탐, 설명 가능성, 자동 조치의 안전성을 관리한다.

## 실무 점검 목록

- [ ] 메트릭·로그·트레이스에 공통 요청·배포·CUJ 식별자가 있는가?
- [ ] 경보가 사용자 영향과 조치로 이어지는가?
- [ ] 즉시 대응용 데이터 경로와 장기 분석 경로를 구분했는가?
- [ ] 클라이언트 경험과 수집 손실을 관측하는가?
- [ ] CUJ 악화 시 배포를 자동 중단할 수 있는가?
- [ ] 보존·접근·삭제·암호화 정책이 데이터 민감도에 맞는가?
- [ ] 경보가 표본 크기와 정상 변동을 고려하는가?
- [ ] 공통 의존성에 따른 상관 장애를 고려하는가?

## 핵심 결론

관측성은 데이터를 많이 모으는 일이 아니라, 사용자 문제의 신호를 연결해 원인을 찾고 안전한 조치를 할 수 있게 하는 능력이다. 신호 상관 관계, 고객 여정, 저잡음 경보, 개인정보 보호를 함께 설계해야 한다.
